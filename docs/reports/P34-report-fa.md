# اصلاح دریافت کانفیگ‌ها — P34

اصلاح در مسیر مشترک دریافت و ذخیره‌سازی نصب شد و همهٔ لینک‌ها و مصرف‌کنندگان خروجی عادی، Smart، Splash و Ads از آن استفاده می‌کنند.

علت اصلی این بود که مهلت شبکه، زمان پردازش و ثبت تک‌تک کانفیگ‌ها را هم شامل می‌شد. پاسخ سالم دریافت می‌شد، اما عملیات محلی با timeout شکست می‌خورد و نسل جدید ورودی‌ها ثبت نمی‌شد. ثبت دسته‌ای، استفادهٔ مجدد از فایل رمزنگاری‌شدهٔ سالم، ایندکس‌های ارجاع و مهلت‌های مستقل این مسیر را اصلاح کردند.

| بررسی زنده | نتیجه |
|---|---|
| اجرای دریافت تازه | هر ۳۳ منبع |
| منابع دارای ورودی | ۳۲ |
| لینک مشکل‌دار workers.dev | سه بار موفق؛ ۱۴۲، ۱۵۱ و ۱۴۹ ورودی یکتا |
| تعداد ورودی دریافتی از همان لینک | هر بار ۱۸۶؛ موارد تکراری جدا محاسبه می‌شوند |
| زمان سه دریافت | ۱۲٫۲۸۹، ۳٫۶۳۹ و ۲٫۸۴۸ ثانیه |
| مجموع ورودی یکتا در لحظهٔ ثبت گزارش | ۷۲۴ |
| سرویس‌ها و پنل موبایل/دسکتاپ | بررسی شدند و فعال‌اند |

Exir در آزمایش پاسخ HTTP200 با بدنهٔ خالی داشت. پاسخ تازهٔ sub ناقص قطع شد؛ ۱۶۱ ورودی قبلی آن تا پایان مدت نگهداری حفظ و نمایش داده می‌شوند. این موارد به‌اشتباه دریافت موفق یا خروجی سالم اعلام نمی‌شوند.

برای جلوگیری از بازگشت همین خطا، آزمون‌های دریافت حجیم، کندی ذخیره‌سازی، پاسخ ناقص، لغو عملیات، ثبت اتمیک و بازیابی worker اجرا شد. در اجرای کامل race فقط یک انتظار قدیمی نام خطا شکست خورد؛ همان انتظار به fetch_timeout اصلاح شد و جداگانه با race گذشت. گزارش اولیه بدون تغییر حفظ شده است. سایر بررسی‌های ساخت، vet، مرورگر و چهار صف بازیابی گذشتند.

بازبینی کد با OpenAI API و مدل gpt-6-astra انجام شد. ایراد پایان فایل رمزنگاری‌شده‌ای که این بررسی یافت نیز اصلاح و آزمایش شد. کانفیگ خام و اطلاعات محرمانه برای مدل فرستاده نشد و اجرای سامانه به API وابسته نیست.

تنظیمات منابع، مدت نگهداری، مشخصات واقعی سرورها و شرط آزمون اتصال برای خروجی سالم تغییر نکرده‌اند. تعداد ورودی با تعداد خروجی تأییدشده یکسان نیست. آزمون Android واقعی و شبکهٔ اپراتورها در این مرحله انجام نشده است؛ رفع این باگ تضمین دسترس‌پذیری دائمی لینک‌ها و سرورهای بیرونی نیست.
