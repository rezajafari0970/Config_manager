## Implementation

- Schema12 adds sources.splash (default false for all existing sources), a pool fingerprint on Smart jobs and separate splash_smart_* tables/views. The existing normal settings/revision and rounds are preserved; Splash defaults enabled with10members and its own revision.
- One SmartPipeline uses closed normal/Splash repository drivers. Selection, composition, core validation, exact proof gates, expiry, self-recovery, randomized delivery and HTTP handlers are shared code. Persistent settings, jobs/member provenance, cache/member provenance, usage counters, rotation/locks, worker state and public token domains remain distinct.
- Admission filters source classification before selection and again through owned-members/ready views. Splash reserves duplicate canonical identities or converted candidate bytes from ordinary Smart while the Splash membership remains retained. Ordinary copies cannot leak the same config back into ordinary Smart. Splash never fills a short pool with ordinary members. Disabling/deleting/expiring a source or its exact proof hides affected cache immediately.
- The source toggle is an explicit desired value plus revision, not a blind inversion. It fences stale requests and obsolete acquisition/Smart completion leases without deleting source bytes or extending TTL. Optional Splash on the old edit API preserves classification when omitted. Bulk import, closed source-row button and edit dialog support the flag.
- /smart-splash and /api/smart-splash expose independent state and links; /api/smart-splash/settings controls its count/enabled state. /smart-splash/json/{id} is canonical individual JSON. /smart-splash-subscription/{token}/configs.jsonl and next.json are separate from normal tokens and rounds. Private /smart-splash/* worker routes exist only on the protected Unix socket.
- A separate systemd supervisor runs config-probe-worker -mode smart-splash with two slots, its own lock and csp sandbox prefix. Integration uses cpt, separate from cst/crw/ctw. No arbitrary untrusted configuration runs outside the existing sandbox.
- A composition blocked by a domain-only pool previously waited for retry even after an independent IP arrived. Eligible-pool identity fingerprints now bypass delay on real membership change while preserving unchanged-pool backoff. Browser fixtures now complete preparation failures as blocked rather than forging a pass with empty bytes.

P22 fixes retained here: validated-cache publication independent of replacement jobs; atomic same-plaintext ciphertext repair; bounded two-dial validated-IP fallback; synchronized compiled plugin registries; bounded worker idle/error polling; scoped UI state and request deadlines; unlinked full-export spooling. See the P22 checkpoint for reproduced faults.

## Deployment and limits

Take a matching stopped-service DB/blob/key/release backup; preserve the live source definitions/counts, enabled states and user Smart count rather than historical values. All existing sources remain ordinary until the user marks them Splash. Activate four supervised services and verify installed/running hashes separately from source publication. Legacy P21 rollback is refused after Splash adoption, because the old builder cannot enforce the new partition; never restore an old production DB over later edits.

Shared SQLite, encrypted vault, conversion proofs and host/network resources remain shared. Modular isolation does not mean separate hardware or independence from total host failure. Compiled driver/plugin extension points are supported, not arbitrary uploaded runtime plugins. Fresh server HTTPS/Instagram-homepage proof is not Android media or carrier evidence. The phone is offline; APK/carrier/2s-best-selection/throughput/loss remain unmeasured. P20 DNS fallback and P21 group-ping limitations still apply.


Final sandbox correction: the new csp/cpt prefixes are explicitly registered. Existing worker/test prefixes previously shared their IPv4 /30 addresses despite different resource names. The sandbox now reserves disjoint address blocks for all active workers and trusted fixture prefixes, retaining crw’s original block and exact cleanup names. Address disjointness and bounds have an unprivileged regression; all real worker/traffic tests must run against this final adapter.


## Adopted-data query correction (schema13)

After the first schema12 deployment, the user added a Splash source. Its15ready profiles correctly remained outside ordinary Smart, but public full Splash export took30.649s for113293bytes/8currently valid profiles and exceeded the browser verifier’s30s deadline. Normal state took11.392s and its full export15.090s in the same observation. Inspection of an isolated live-data snapshot identified the correlated identity-OR-candidate reservation scan in normal smart_inputs; repeated normal claims/readiness checks held the shared database connection and delayed Splash reads.

Schema13 replaces that scan with two non-null sets evaluated in the current SQL statement, preserving exact identity/candidate priority without storing a stale membership cache. The migration changes only the view and version marker. A regression constructs the actual schema12 DDL with both adopted pools, published caches/settings/rounds, upgrades twice and compares every published byte and control. Missing candidates and subsequent classification changes are covered. Existing alias, duplicate, disable/delete/expiry/proof, concurrent-slot and browser tests run against schema13. The same-snapshot benchmark and rollback/re-upgrade receipt is .local/p23-r2-dbbench.json; final live timings are in .local/p23-public.json. No source is automatically marked for testing.

Adopted-snapshot measurements (seven reads per view, fixed SQL clock): smart_ready median405.619→19.020ms (37identical rows); smart_refresh_needed408.913→24.330ms (266identical rows); smart_inputs32.077→1.767ms (315identical rows). Splash readiness itself was not the expensive query (0.232→0.482ms medians under varying host load); it was delayed behind ordinary work. Every persistent table fingerprint matched before/after13migration, schema12 rollback using the actual previous binary, and re-upgrade. These are isolated database timings, not mobile throughput.

Parallel normal/Splash worker validation also exposed a test-harness collision: both fixtures bound18195, so a Splash readiness request could reach the other fixture before its own schema existed. Each fixture now owns an OS-assigned loopback listener, publishes its own origin/scope file only after seeding, and builds a private binary; diagnostics are scope-specific. Both worker suites are rerun concurrently to verify the isolation. Production listeners and routes are unchanged.
