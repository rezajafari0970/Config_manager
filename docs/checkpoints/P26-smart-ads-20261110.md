# P26 — independent Smart Ads

The user requests a third output type: one healthy Splash Ads input replaces the fixed ads-01, chained through ordinary Smart leastLoad. Every unique eligible Splash candidate has its own profile and independent durable delivery round. This authorizes the extra Ads routes and carrier links; ordinary Smart, Smart Splash and normal conversion envelopes remain unchanged.

## Implementation

Schema15 is additive. ads_smart_* repositories isolate settings, jobs, cache provenance, counters, turns and worker status. The common SmartPipeline uses closed SQL identifier drivers and the existing fair source/member selector. The configured count means main inputs; exactly one whole Splash input is additional. Heads come only from Splash and followers only from the ordinary pool. Current source/raw/candidate identity, enabled/control state, fresh HTTPS+Instagram proof and shortest TTL gate every claim, renewal, completion and export. Position0 must retain Splash ownership; other positions must retain ordinary ownership. New Splash arrivals join the next ready round. HEAD/prefetch do not consume turns; no-ready single returns503.

ComposeAds reuses the Smartv8 composer, copies all source outbounds, retains namespaced dependency chains, adds the main carrier only at terminal dialers, and preserves UDP/UDP443 policy. An entire balanced Splash input remains one selected input with an isolated Ads exit pool; it is never silently reduced to one child or mixed into main/bootstrap. Active incompatible custom dialers or ambiguous nested chains fail explicitly. No new direct fallback is generated. Main/bootstrap leastLoad remains expected3/maxRTT2s/tolerance0.15; burst15/3/5, dual tunneled bootstrap, logging off and local metrics remain. Delivery shuffles only main proxy slots; the first remains an independent main IP entry for Lib40 RealPing.

The user-supplied Ads list includes geosite:google@ads plus explicit BrowserLeaks/Google advertising domains. The geosite asset is required and pinned in deploy/ads-assets.json, copied into the pinned core asset directory and mounted read-only by the existing sandbox. A missing asset blocks core validation. This is not a complete classification of all Google or third-party ad traffic.

New UI/API/canonical/full/single surfaces use /smart-ads, with independent settings and distinct main/Ads eligibility counts. The production service config-repair-ads uses a private Unix queue, separate lock, csa resource names and disjoint address range; integration uses cat, controlled traffic csta. Existing scopes and immutable source bytes remain intact.

## Rollback

Stop all five services, retain current data, disable the Ads service, set user_version14 only for this additive migration and activate the matching P25 binary/driver. Leave added tables/columns intact. Do not restore an older DB over later user changes. Preexisting Smart/Splash operation is preserved; Ads publication is unavailable on the previous binary. Re-upgrade may rebuild Ads blobs removed by older GC. Earlier pre-Splash downgrades remain forbidden.

## Live-source compatibility found during acceptance

After initial deployment, three currently marked Splash sources had no fresh eligible members. Thirty-one VLESS REALITY records were blocked by support-x25519mlkem768=true. This extension is a Mihomo compatibility hint emitted by 3x-ui; pinned Xray's REALITY UClient builds the native uTLS handshake and its REALITYConfig has no corresponding JSON field. The positive true/1 hint is now accepted only for VLESS REALITY, preserving identical native candidate bytes and the immutable original. False/0, malformed, duplicate and wrong-protocol/security uses are rejected explicitly. Other unknown parameters remain rejected. No fingerprint, key, TLS validation or proof gate is changed.

Primary reference: https://github.com/MHSanaei/3x-ui/commit/ce221c33d038a7c6c0d06c5ba013c7694d7a10a3 ; pinned local Xray source infra/conf/transport_security.go and transport/internet/reality/reality.go. Current upstream context: https://xtls.github.io/en/config/transports/reality.html . This is not a claim that every supplied fingerprint negotiates ML-KEM or that every server accepts the connection.

A narrow deployment retry selects only current Splash originals with the exact positive hint that the final converter accepts, and reschedules only blocked unknown_query_parameter jobs. No successful receipt is synthesized; actual sandbox tests must produce fresh public+Instagram proof. Scheduled retries also handle future arrivals automatically. Templatev4, Smartv8 and schema15 stay unchanged.
